# 2026-08-19: v8 re-bench on smolquery 0.13.0

Third run in the v8 series, after the 0.13.0 deploy completed at ~00:45Z.
Same shape as the two prior runs
([morning](2026-08-18-v8-seal-compaction.md),
[post-T304](2026-08-18-v8-post-t304-rebench.md)): 16 VUs, 30 s measured,
600 s compaction watch, `otel_logs_v8` (appends). All nine pods ran image
`ghcr.io/chasers/smolquery@sha256:20d87cda…`. The redeploy zeroed the
counters. Metrics database:
`results/raw-loadgen/loadgen-20260819T004709Z-0-13-0.metrics.sqlite3`.

The v6 and v7 corrupt segments were remediated before this run, so the
poison compaction loops from the prior two runs were gone from the start.

## Verdict

**The first clean v8 run.** Throughput rose 14% over the morning baseline.
The seal work spread almost evenly. Zero seal errors, zero compaction
failures, zero refusals — and **zero pod restarts**. Both prior runs
OOMKilled a storage pod during the seal drain; this one did not.

Separately, the pruning bench's timed cases turned out to measure a fixed
per-query floor, not pruning. An `explain` through the API settled it —
see "Pruning" below.

## Pruning: the timed cases measure a floor, not pruning

The timed numbers looked alarming — the empty-date `scan` (4,093 ms) cost
the same as the no-filter control (4,018 ms), against a 180x win on
2026-08-16. **Pruning is fine.** The router's `"explain"` option settled
it (`"explain": "plan"` or `"analyze"` in the `POST /v1/queries` body):

- The empty-date plan collapses to `EMPTY_RESULT` at bind time. The
  engine proves from file statistics that no sealed file overlaps 1971.
- `EXPLAIN ANALYZE` reports the engine's total time as **0.0064 s**,
  inside a job whose `durationMs` is 1,321 ms.

The wall time is a **fixed per-query floor**, ~1.3 s idle and ~3–4 s
right after ingest. A `trace: true` run breaks it down: `engine_start`
524 ms, hot-tier `manifests` 1,094 ms (nine `manifest_fetch` calls across
the three buffer pods, ~350 ms each), `execute` 22.6 ms. Every case pays
the floor, so every case lands near the same wall time. The 2026-08-16
run showed a 180x ratio because its control scan dwarfed the floor.

Two smolquery findings to file:

1. **The `statistics` block is wrong for pruned queries.** The
   `EMPTY_RESULT` job reports `sealed: filesScanned 9 of 9,
   rowsScanned 22,374,034, 311.66 MiB` — the plan-time file inventory,
   not real reads. The profiler shows zero reads.
2. **The hot-tier manifest fetch dominates idle query cost.** ~350 ms per
   buffer-pod call, three rounds; each round has one fast (~1 ms) pod and
   two slow ones.

The pruning bench now records an `"explain": "analyze"` plan and its
engine time per case (`engine_total_s` in `*.prune.json`), so the next
run can see through the floor.

## The 4-point VU sweep

A follow-up ingest-only sweep, same table, 30 s per point, back to back
(metrics database:
`results/raw-loadgen/loadgen-20260819T012514Z-0-13-0-sweep.metrics.sqlite3`):

| VUs | rows/s | p50 / p95 / p99 ms | refused | cluster CPU avg | buffer RSS peak |
|---|---|---|---|---|---|
| 4 | 91,801 | 125 / 175 / 202 | 0 | 592% | 2.6 GB |
| **16** | **157,204** | 282 / 522 / 700 | 0 | 865% | ~4.0 GB |
| 32 | 143,196 | 568 / 1,196 / 1,286 | 18 | 779% | **4,096 MB (limit)** |
| 64 | 107,086 | 1,555 / 2,244 / 2,610 | 182 | 641% | 4,096 MB (limit) |

**The curve peaks at 16 VUs, and the ceiling is buffer-pod memory, not
CPU.** At 32 VUs the buffer pods pin their RSS at exactly 4,096 MB — the
container limit — and the 429 refusals start. At 64 VUs the storage pods
sit at the same limit. Cluster CPU *falls* past the peak (865% → 641% of
~1,370% available): the pods spend the load shedding and waiting, not
working. The refusals are the bounded admission path doing its job — zero
errors, zero restarts, zero OOMKills across the whole sweep, including
the two points that ran flat against the memory limit.

Two caveats on reading the numbers:

- The 16 VU point here (157,204) is 21% below the standalone run an hour
  earlier (200,253). The points ran 18 s apart, so each point ingested
  while the previous point's seal drain still ran. The standalone
  number is the clean one; the sweep shows the shape, not the peak.
  The harness now closes this hole: since this sweep, every VU point
  waits for an empty hot tier (`statistics.hot.filesTotal == 0`) before
  its warm-up, and records the wait as `drain_wait_s` in `*.pods.json`.
- Seal spread over the sweep was 43% / 27% / 30% — rougher than the
  clean run's 32/32/35, measured under continuous pressure.

Raising the buffer pods' memory limit is the obvious next experiment if
the 32–64 VU range matters.
