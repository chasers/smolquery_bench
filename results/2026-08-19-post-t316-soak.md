# 2026-08-19: the post-T316 soak — much faster, still collapses

Plan: repeat the 03:14Z soak exactly — 16 VUs against `bench.otel_logs_v8` —
on the build that landed T-315, T-316, T-317, T-318 and T-320, and read whether
ingest still degrades. Same table, same VUs, same cluster shape, so the two runs
compare minute for minute.

Actual: **the pipeline got much faster and the unattributed span nearly closed.
The buffer tier still OOMKills, on the same timescale as before.** The operator
stopped the run at 21:54Z, about 7 minutes into the measured window.

## The refusals are not admission control

This is the finding that matters for the sustainable-rate criteria.

| | count |
|---|---|
| api 2xx | 16,823 |
| api 4xx | **0** |
| api 5xx | **15,851** |
| `buffer_admission_refused_rows_total` | **0** |

**48.5% of api responses were 5xx, and admission refused nothing.** k6's 31,880
"refusals" are connection resets and 5xx from dying pods, not load shed on
purpose. The 01:25Z burst sweep behaved the opposite way — 18 refusals at 32 VUs
and 182 at 64, every one a 4xx, no 5xx at all.

A pass criterion written as "refusals under 0.1%" passes this run. Count 5xx
separately.

## The new counters earn their place

T-315's instrumentation makes the hot tier legible for the first time.

**The scoped fetch works.** Per request, across the run:

| route | bytes/request | entries/request | total |
|---|---|---|---|
| `manifest` GET (unscoped) | 4.4 KB → **26,663 KB** | up to 3,562 | 188.9 MiB |
| `manifest_scoped` POST | 0.4 KB → 354 KB | up to 898 | **1.6 MiB** |
| `segment` GET | — | — | **1,890.8 MiB** |

The scoped route serves ~0.39 KB per entry against ~7.6 KB unscoped — a 19×
reduction, because it drops the 63-column stats block. Total manifest traffic
from the sealer fell to 1.6 MiB.

**The ETS read cost splits the same way.** `smolquery_hot_manifest_read_microseconds_total`:

| op | range |
|---|---|
| `claimable` (scoped, new) | 20 → **262 µs** |
| `entries` (full scan) | 27 → **178,635 µs** |

A single `entries` read reached **179 ms**, 680× the worst `claimable` read.
That read is O(backlog) and it runs on the buffer pod.

**Byte volume is dominated by segment reads, not manifests.** 1.85 GiB of
micro-segment bytes left the buffer pods in about 8 minutes, against 189 MiB of
unscoped manifest and 1.6 MiB of scoped. Those are `max − min` per pod, so
restarts undercount them: read them as lower bounds.

## What is fixed

1. **The unattributed span.** 79% of request time had no counter behind it on
   0.13.0. It is now 16–45%, and the write phase tops out at 328 ms instead of
   795 ms. T-181 called the missing 830 ms "the whole ballgame"; most of it is
   now accounted for or gone.
2. **Peak throughput, up 51%** — 208,943 against 138,453 rows/s.
3. **The sealer's manifest fetch.** Two full fetches per attempt became one
   scoped, stats-free fetch. `merge.ex` no longer fetches at all.
4. **Recovery under load.** The 0.13.0 soak decayed monotonically and never
   came back while load ran. This one oscillates and repeatedly returns above
   100k rows/s between OOM cycles.
5. **No collateral damage.** Zero api and zero storage restarts, against five
   last time.

## What is not

1. **The buffer OOM.** Still the binding constraint, still at the 4 GiB limit,
   still ~2.5 minutes into sustained 16 VU load. Every pipeline timing looked
   healthy at 21:48 and the pods died anyway.
2. **The unscoped manifest route is still O(backlog), and only the query
   planner calls it.** `query_service/planner.ex:310` calls
   `HotClient.manifest(url, partition, timeout_ms: ...)` with no ids and no
   `stats: false`, per partition ref, per query. It served a **26 MB** response
   at 21:49, the minute the pods went down. The planner prunes on those stats,
   so it cannot simply pass `stats: false` — the fix is narrower: stats for
   referenced columns only, or push the pruning conjuncts to the buffer, or
   paginate.
3. **Sealing still cannot keep pace.** 521 segments sealed against ~11,940
   commits — 4.4%, worse than the 17–69% range of earlier runs, because the
   pods spent most of the window dead. Errored attempts averaged 889 segments
   against 74 for successful ones.
4. **A hot file that never seals.** The drain gate waited its full 300 s on one
   file, despite `seal_max_age_ms: 60_000`. It predates the run.

## Next

1. Buffer memory is now the whole problem. Raise the limit to 8 Gi and repeat,
   as a control — that separates an under-provisioned tier from unbounded
   growth.
2. File the planner's unscoped manifest fetch against the tracker, under PL-45.
3. Re-run at 8 VUs and 4 VUs to bracket a sustainable rate now that the
   pipeline is faster. The 16 VU burst peak moved, so the old brackets are stale.
4. Add a 5xx criterion to the sustainable-rate plan before any hold runs.
