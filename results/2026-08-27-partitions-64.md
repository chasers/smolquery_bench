# 2026-08-27: the pathological table — 64 write partitions, 30 days of timestamps

**Ingest gets faster, everything after it gets much worse.** With the
table's write-partition count raised from the deployment's 3 to the
maximum of 64 and every body's timestamps spread over 30 days, 32 VUs
pushed **111,836 rows/s** (against 84–98k on the same shape at 3
partitions) with zero refusals — and during that minute the four-project
tail query took **p50 7.2–7.5 s, p95 21–22 s**, one query hit the 30 s
timeout, each query saw a median of 633–677 hot files (up to 1,972), the
hot tier took **269 s** to drain (95 s at 3 partitions), and a one-day
`timestamp` bound reads **every one of the 128 sealed files**.

**smolquery has no partition key.** `PATCH …/tables/:t` takes
`clustering` (a sort) and `partitions` (a write-partition count, hash of
the batch id, at most 64, raise-only, never below
`SMOLQUERY_WRITE_PARTITIONS`; `docs/api.md:42`, T-304). This run is the
nearest analog of ClickHouse `PARTITION BY (project, toDate(timestamp))`
on a 1,000-project stream, and it shows what that count is for: **seal
parallelism across storage nodes, not data layout.** A partition takes
whole insert bodies, so every partition still holds every project and
every day.

## Setup

- Cluster: smolquery `main@43f1b30`, three query pods
  (`SMOLQUERY_WARM_ENGINES=4`), api pods `api,ingest`, 3 buffer and 3
  storage pods; `SMOLQUERY_WRITE_PARTITIONS=3`. Zero restarts.
- Table `bench.clickstack_map_p64`, fresh: the clickstack map schema,
  clustering `[project, timestamp]`, `partitions: 64` set through the
  harness's new `PARTITIONS` knob.
- Body: `SHAPE=clickstack DAYS=30` — `tools/genbody -days 30` subtracts a
  uniform 0–30 days from each row's `timestamp` (31 distinct dates in the
  3,062-row body); `inserted_at` is still the request stamp.
- `mise run bench-tail`: four queriers on the query pods, the narrow
  windowed query (`timestamp, trace_id, span_id, body`, `inserted_at >=
  now − 300 s`, `LIMIT 100`), 60 s phases, one 32-VU ingest point.
  21:27–21:38Z, box `i-0460b308e71aa0ce5`.
- Comparison: `-tail4-warm4` on `clickstack_map_v2` (3 partitions, one
  day) an hour earlier, same query, same cluster.

| tail under ingest, p95 / p99 | 3.9–4.3 / 4.6–4.8 s | **21–22 / 25–26 s**, one 504 (30 s timeout) |

| drain after the point | 95 s | **269 s** |
| tail sealed, p50 / p95 | 1.47–1.50 / 1.79 s | 1.18 / 2.9–3.0 s (window mostly empty after the long drain) |

Seal counters over the run: **128 seals** for 8,656,274 rows — 67,600 rows
per seal against ~400,000 at 3 partitions — 2,791 hot segments consumed,
5.4 s per seal, **689 s of seal work for 60 s of ingest**. Sealed size
175,124,600 B, **20.2 B/row against 5.7** on the same body shape: smaller
files dictionary-encode worse. Buffer pods peaked at 3,046 MB of 4,295;
nothing was killed.

Hot-server traffic over the run: 119,366 segment GETs and 200,025 HEADs.
The idle and sealed phases contribute almost none of that; in the ingest
minute each tail query opened hundreds to ~2,000 micro-segments, because
64 buffers each flush their own small segments and the query's hot side is
`read_parquet([every one of them])`. This is T-400's problem at 10× the
segment count.

### What a date bound does now

On the idle table afterwards, with explain:

| query | files read | engine |
|---|---|---|
| `p64`: `count(*)` for one day of `timestamp` | **128 of 128** | 0.94 s |
| `p64`: the same plus `project = 'proj_0617'` | 128 of 128 | 1.22 s |
| `v2` (one-day timestamps): `count(*)` for that day | answered from statistics | 0.000 s |

Every `p64` file spans all 30 days, so a day bound prunes nothing and the
scan reads every file; on `v2`, whose rows all carry one day, the same
bound is answered from file statistics without a scan. Time-contiguous
ingest is what makes a `timestamp` bound cheap; a stream whose event
times arrive out of order over a month loses it entirely, whatever the
partition count.

## Read it as

1. **`partitions` is a throughput knob with a query bill.** It raises the
   seal fan-out (`min(P, N)` storage nodes) and the ingest rate, and it
   multiplies the micro-segments a query must open while they are hot, the
   seal count, and the sealed bytes per row. At 64 the tail query is
   unusable under load and the hot tier lags ingest by minutes.
2. **Out-of-order event time defeats the one pruning that works.** The
   sealed tier prunes on `timestamp` only because sealing is
   time-contiguous. With a 30-day spread per body, a day bound is a full
   scan — the same "every file holds everything" shape T-393 found for
   `project`.
3. Neither knob gives a per-project or per-day layout. That needs a
   partition key on the write path — the item costed separately in the
   T-393 write-up — or, for the tail query, T-400.

## Caveats

- One run, 60-second phases, one table with 8.7M rows. The direction of
  every number is large enough to stand; the absolute values are one
  sample.
- The `p64` sealed phase ran after a 269 s drain, so its 5-minute window
  was empty for 67 of 84 queries; its p50 measures the empty-window floor
  with 128 sealed files, not a tail read.
- 64 partitions on 3 buffer pods is 21 buffers per pod. The 2026-08-21
  memory ceiling was reached with 3; 60 seconds at 32 VUs peaked at
  3.0 GB with no restart. A soak would be a different story.
