# Local re-bench on smolquery 0.11.0, 2026-08-17

The first local bench since 2026-08-11. Every run between the two dates went to
the deployed cluster, not this machine.

**Both arms lost throughput at 8 and 64 VU, by about the same amount. The client
got heavier, not the server slower.** The `inserted_at` stamp makes k6 rewrite
6.87 MiB on every request, and k6 shares the ten cores with the server.

## Findings

**The load generator explains most of the drop.** At 64 VU k6's own CPU went
44.7% → 133.6% in the ClickHouse arm and 56.5% → 158.0% in the smolquery arm,
roughly 3×. Its peak RSS went ~1.9 GB → 4.2–6.5 GB. The 2026-08-10 body carried
no `inserted_at` placeholder, so k6 sent one `open()`ed buffer. It now splits and
joins a 6.87 MiB string per request per VU. Server plus client plus background
load reaches ~770% of 1000% at 64 VU. Both arms pay it, and both lost 37–39%.
**Do not read these two rows as a server regression.**

**The low-VU floor is gone in mainline.** `config/config.exs` now ships
`commit_siblings: 5` and `flush_idle_interval_ms: 5`, so a default build behaves
like the PR #124 `sib5` arm with no flag set. 1 VU went 2,886 → 44,016 rows/s
(15.3×) at p50 1,062 → 56 ms. 4 VU went 10,817 → 99,893 (9.2×). This holds up
despite the heavier client, because low-VU runs never saturate the machine.

**smolquery now leads ClickHouse at 1 VU by 32%** — 44,016 against 33,324, at a
better p50 (56 ms against 81 ms). The 2026-08-10 baseline had ClickHouse 13×
ahead there.

**The two arms tie at 64 VU.** 290,753 against 290,385, a ratio of 1.00 where the
baseline read 1.05. smolquery keeps a much better latency profile at that point:
p50 335 ms against 499 ms, p99 729 ms against 1,185 ms. It buys that with 1,566
refusals, which ClickHouse does not have.

**Refusals at 64 VU rose 76 → 1,566, and they reproduce.** A repeat run gave
1,562. The server hits `MAX_BUFFERED_BYTES=128MiB` and answers 429 `buffer_full`.
A slower drain under a saturated machine is the likely cause, but this run does
not prove it. **Repeat it on a quiet machine before you call it a regression.**

**The 1M-row row groups are not the cause.** Commit `52f03cc` (T-280) raised
`seal_row_group_size` 16,384 → 1,048,576, and the first 64 VU run logged one
DuckDB seal failure: `Out of Memory Error: failed to allocate data of size
12.0 MiB (1.8 GiB/1.8 GiB used)`, against the writer's 2 GB `memory_limit`. A
64 VU A/B with `SEAL_ROW_GROUP_SIZE=16384` gave **297,208 rows/s and 1,562
refusals**, against 290,753 and 1,566. Both sit inside the ±3–4% band. The
smaller row groups logged no seal failure, but one event against zero proves
nothing. The OOM is worth its own ticket. It is not what moved these numbers.

## Caveats

- One 60 s run per point. Variance is ±3–4%, so read any delta under 4% as flat.
- The machine carried 192% background load, against 136% on 2026-08-11. It
  affects both arms alike.
- `otel_logs_v3` clusters by `project_id` alone on the smolquery side. The
  `otel_logs` table of the 2026-08-10 baseline clustered by
  `[project_id, timestamp]`, and ClickHouse now adds
  `PARTITION BY toDate(inserted_at)`.

## Next step

**Take the stamp off the hot path before the next local baseline.** Pre-stamp a
pool of bodies at generation time, or let k6 patch the fixed-width field in a
byte buffer instead of splitting a string. Until then, the 64 VU rows measure the
laptop, not the server.

# Post-fix sweep, 2026-08-17 11:30

The same protocol, after the T-285 flush re-arm landed (`072a26a`) and the k6
byte-patch stamp replaced the string rewrite. 60 s measured, 20 s warm-up, cold
table per run, background load 188% — the same condition as the morning runs.

| VU | smolquery | ClickHouse | ratio | smolquery p50 |
|---|---|---|---|---|
| 1 | **43,552** | 37,202 | **1.17** | 67 ms |
| 4 | 104,193 | 235,115 | 0.44 | 117 ms |
| 8 | 155,442 | 310,998 | 0.50 | 150 ms |
| 16 | 209,311 | 311,375 | 0.67 | 200 ms |
| 64 | **crashed** | 390,389 | — | — |

Zero refusals on every completed run.

**The T-285 fix narrows the dip; it does not close it.** At 8 VU the ratio moved
0.46 → 0.50. That matches the knob A/B, which showed the re-arm captures about
43% of the available headroom — it only fires when `in_flight_inserts` actually
falls below `commit_siblings`, and at 8 VU it often does not. The rest needs a
byte target that scales with the arrival rate.

**16 VU is the fix's best point**: 209,311 rows/s at ratio 0.67, the strongest
mid-range result smolquery has recorded here.

**64 VU crashed** — the T-286 SIGBUS, not a throughput result. Earlier 60 s runs
at 64 VU on the same build reached 327,068 rows/s. Treat any single 64 VU number
as suspect until T-286 is fixed.

Raw JSON: `results/raw-0817-final/`. Measured on Erlang/OTP 29.0.2; see
[2026-08-17-otp-27-vs-29.md](2026-08-17-otp-27-vs-29.md).
