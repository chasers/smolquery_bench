# 2026-08-16 (post-245): admission holds the door, three pods still die

**The result is a bug report, not a baseline.** The deploy fixed the shape of
the load but not the memory ceiling. Three pods OOMKilled, one more than the
pre-deploy sweep. Throughput rose to 113k rows/s, but every step above 8 VUs
measures a cluster that is losing pods.

This sweep tests the three commits that landed after
[2026-08-16-loadgen-t245-oomkill.md](2026-08-16-loadgen-t245-oomkill.md).

## Setup

- Load generator: c7i.2xlarge (`i-0f8592b0e51925754`), eu-central-1a, posts to
  the api pod at `http://10.61.4.219:4000`. Terminated after the run.
- Target: `bench.otel_logs_v2`, cluster on `main@10b019b`, image
  `sha256:fe24bd51`. Pods started 14:43 UTC; the sweep ran 14:54 to 14:59 UTC.
- Deployed for the first time: PR #166 (T-262, derived row cap), PR #167
  (T-245, bounded admission), PR #169 (T-264/265/266, review fixes).
- Sweep: 8 to 128 VUs, 30 s measured per step, 3,062 rows per 6.87 MiB body.

## T-245 fires, and it is not enough

Admission works. Refusals climb 0 → 0 → 64 → 464 → 1,205 across the sweep, and
the api pod logs its bound at start:

    ingest admission limit=805306368 bytes in flight

That is 768 MiB, a quarter of the api pod's 3 Gi limit. At 6.87 MiB per body it
admits about 111 concurrent bodies.

The pod still died. `api-0` peaked at **3,067 MB against a 3,072 MB limit**.

**The bound measures the wrong quantity.** It counts raw body bytes in flight.
What fills the pod is the parsed and decoded form, which is several times
larger. A 768 MiB admission budget therefore permits a resident set far past
768 MiB. The pre-deploy sweep supports this: `buffer-0` died at the 16 VU step
with only ~110 MiB of bodies in flight, a level this bound never refuses.

T-245 changed the failure from an unbounded queue to a bounded one. It did not
make the bound small enough to protect a 3 Gi pod.

## storage-0 died in a seal, not a compaction

    14:58:53 [warning] seal of {"bench","otel_logs_v2__p2"} failed:
             {:merge_failed, %Smolquery.Engine.CallExited{reason: :timeout}} (1 consecutive)
    14:59:58 [warning] seal of {"bench","otel_logs_v2__p2"} failed: ... (2 consecutive)
    15:00:06 OOMKilled

This is the **merge** engine at 2048MiB, not the compaction engine at 1024MiB:

    storage merge engine memory_limit=2048MiB (half the cgroup memory limit)
    storage compaction engine memory_limit=1024MiB (a quarter of the cgroup memory limit)

The seal path is the T-244 problem, back at a higher throughput. One thing did
get worse. On 2026-08-14 and 2026-08-15 the seal tasks died and their
supervisor respawned them, so the pod survived. Here the kernel killed the pod.
**The task-level containment did not hold at 113k rows/s.**

## The compaction fix is untested

`bench.otel_logs_v2` did not compact once during or after this sweep. The only
compaction since the redeploy is `smoke.events` at 14:48:30, on two segments,
and it succeeded.

So PR #166 and PR #169 are deployed and unexercised. The seal failures sit
upstream of compaction: segments never landed, so no group formed to merge.
The 45% failure rate this deploy targets is neither confirmed fixed nor
reproduced.

`row_caps` also live in the compactor's process state, so the three restarts
during this window each reset the learned caps to the derived 2Mi rows.

## Harness: LABEL_SUFFIX never worked here

The previous page told the reader to set `LABEL_SUFFIX` before an A/B sweep.
That advice was wrong for this path. `scripts/loadgen.exs` hardcoded

    label = "loadgen-vus#{vus}"

and ignored the variable; only `scripts/bench.exs` read it. So this sweep
overwrote the pre-deploy raw files a second time, despite the flag being set.
The numbers survive only in the two dated pages.

`scripts/loadgen.exs` now applies the suffix to both the k6 and the pod output.
`RESULTS` always worked and remains the safer choice, because the load
generator keeps its own `results/` directory across runs, and `fetch` extracts
that whole directory over the local one.

## Next

1. **Bound the parsed size, not the wire size (T-245 follow-up).** The api pod
   needs a limit that tracks resident cost. A 768 MiB wire budget does not
   protect a 3 Gi pod.
2. **Re-open the seal path (T-244).** The merge engine at 2048MiB now kills its
   pod instead of losing a task. Contained failure was the property worth
   keeping.
3. **Re-test compaction under load that survives.** PR #166 and #169 cannot be
   judged until segments land. Run a sweep capped at 8 to 32 VUs, where no pod
   died, and let compaction work through the backlog.
4. **Sample wide.** Monitor for one hour after the sweep, not only during it.
   `storage-0` died 7 minutes after the last request.
