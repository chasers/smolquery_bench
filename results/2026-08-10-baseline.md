# Baseline: smolquery vs ClickHouse ingest, 2026-08-10

First full run of the harness (commit `5a99fa6`). Closed-loop VU sweep, cold
table before every run, identical 3,062-row × 62-column NDJSON body
(~6.74 MiB) POSTed to both systems. Protocol per run: preflight insert →
20 s warm-up → 15 s pause → 60 s measured. Durability parity: smolquery
fsyncs before acking 200; ClickHouse ran with `fsync_after_insert = 1,
fsync_part_directory = 1` and `async_insert` off.

## Environment

| smolquery | `2519d23` (+3 locally modified files), DuckDB writer, Elixir 1.20.2 / OTP 29 |
| smolquery tuning | `FLUSH_MAX_BYTES=48MiB`, `FLUSH_INTERVAL_MS=1000`, `WRITE_POOL_SIZE=10`, `ENCODE_CONCURRENCY=10` (= schedulers online), `MAX_BUFFERED_BYTES=128MiB` — both tuned values come from the sweeps in Tuning below |
| ClickHouse | 26.7.3.19 (brew), table-level fsync settings only |
| Load | k6 v2.2.0, same machine as the server (shared caveat; k6 CPU tracked per run) |

The machine had rebooted for a macOS update ~2 h before; runs started only
after load and Spotlight/installer CPU stayed quiet for a sustained minute.

## Findings

**Whether the 128 MiB buffer collapses at 32 VU depends on drain rate, not
buffer size.** At the earlier 4/4 tuning, 32 VUs × 6.74 MiB ≈ 215 MiB of
bodies in flight overwhelmed `MAX_BUFFERED_BYTES=128 MiB` and throughput
collapsed to 78,586 rows/s behind 353,320 refusals (429 `buffer_full`).
At 10/10 the pipeline drains as fast as the load feeds it: the same
128 MiB config accepts every request through 32 VUs and refuses only 76
of ~9,600 at 64 VUs (a probe with a 256 MiB cap was slightly worse — a
deeper backlog just queues longer). The buffer cap is a symptom knob;
pipeline width is the real one.

**Low-VU smolquery rows are the ack-cadence floor, by design.** Below ~5 VUs
the 32 MiB flush trigger is never reached, so every request waits out the
1,000 ms `FLUSH_INTERVAL_MS`; p50 ≈ 1.1 s and 2.9–10.8k rows/s reflect the
configured durability cadence, not a throughput ceiling.

**Peak vs peak, smolquery leads by ~5% — but ClickHouse wins everywhere
below 64 VUs, with much better latency.** smolquery's 480,569 rows/s
@ 64 VU edges ClickHouse's 457,472; at 1–32 VUs ClickHouse is ahead at
every level (13× at 1 VU, 24× at 4). Both readings are gentler than the
load-rig reference's 2.3× smolquery win (383,157 vs 165,814 on an
M1 Pro / 16 GB), chiefly because **ClickHouse-with-fsync runs 1.6–2.7×
its reference numbers here** (e.g. 264,832 @ 4 VU vs 165,814). An `FSYNC=0` probe
explains most of it: on this machine the fsync settings cost ClickHouse
~3% (273,014 rows/s no-fsync vs 264,832 with, @ 4 VU), where the reference
setup paid 54% (359,141 → 165,814) on ClickHouse 25.8 LTS. The settings do
apply — verified three ways: the settings appear in the table's
`engine_full`, and per `system.events` one insert performs 10 `FileSync` +
2 `DirectorySync` calls costing ~2.2 ms (0 calls with `FSYNC=0`), matching
the measured p50 delta. fsync is cheap here because the ~6.7 MiB insert
builds a *compact* part (~10 files to sync, not 2 per column) and macOS
`fsync(2)` doesn't flush the drive cache. The reference's headline
also compared smolquery's 32 VU peak against a ClickHouse-fsync arm
measured only at 1 and 4 VUs, before concurrency amortizes fsync latency.

**Durability parity is real but weaker than it sounds on macOS.** Plain
`fsync(2)` on Darwin does not flush the drive's write cache (that requires
`F_FULLFSYNC`), and both arms sync this way — smolquery via the BEAM's
`file:sync`, ClickHouse via its fsync settings. Both arms' 200s mean
"synced past the page cache", not "survives power loss", equally.

## Tuning

### WRITE_POOL_SIZE / ENCODE_CONCURRENCY

The baseline's 10/10 tuning comes from this sweep, run at 32 VU with the
256 MiB buffer while the then-baseline used the load-rig reference tuning
of 4/4 (smolquery's stock defaults are far lower: `write_pool_size: 1`,
`encode_concurrency: 2`):

| pool/enc | rows/s | p50 ms | p99 ms |
|---|---|---|---|
| 4/4 | 306,287 | 302 | 567 |
| 6/6 | 336,106 | 270 | 593 |
| 8/8 | 352,524 / 376,385 (two runs) | 257 / 242 | 537 / 492 |
| 10/10 | 353,527 | 248 | 721 |
| 12/12 | 369,011 | 245 | 509 |
| 16/16 | 369,840 | 241 | 535 |

- **The knobs must move together.** Raising either alone (8/4 or 4/8) held
  throughput flat and produced 429 storms — the narrower stage backs the
  buffer up. Encode and write are pipeline stages; only balanced widening
  helps.
- **The plateau starts at 8/8**: run-to-run variance is ±3–4% (two clean
  8/8 runs spanned 352–376k), and everything from 8/8 through 16/16 sits
  inside that band. The baseline adopts 10/10 — on the plateau and equal to
  `System.schedulers_online()` on this machine, so it generalizes as
  "pool = enc = core count" rather than a hand-tuned constant.
- **DuckDB threads are not the lever.** smolquery divides its engine
  thread count across pool members (pool=8 → 1 thread each). A control run
  pinning `WRITE_ENGINE_THREADS=2` (16 total DuckDB threads vs 8) measured
  347,445 — inside the noise band. The ceiling comes from somewhere else
  (BEAM-side encode, buffer hand-off, flush cadence, or memory bandwidth).

### VU scaling and FLUSH_MAX_BYTES

Probing past 32 VUs (at the then-default 32 MiB flush) showed the closed
loop, not the server, was the limit at 32: throughput rose 383,597 →
394,353 → 414,700 → 419,237 at 32/48/64/96 VUs, then fell to 382,362 at
128 as backpressure churn set in — with server CPU never above ~535% avg
of 1000%. The best operating point is 64 VUs, so the baseline sweep now
includes it for both arms.

`FLUSH_MAX_BYTES` at 64 VUs is a strong lever with an interior optimum:

| flush size | rows/s | p50 ms |
|---|---|---|
| 8 / 16 MiB | server crashed | — |
| 32 MiB | 414,700 | 429 |
| 40 MiB | 459,845 | 373 |
| **48 MiB** | **491,098 / 510,924** (two runs) | 343 / 341 |
| 56 MiB | 497,993 | 334 |
| 64 MiB | 439,598 | 375 |

The baseline adopts 48 MiB. The trade is VU-dependent: vs 32 MiB it is
+15% at 8 VUs, −4–8% at 16–32 VUs (bigger batches fill slower at moderate
load; at/near the run-variance band), and +16% at 64 VUs. 64 MiB likely
suffers from crowding the 128 MiB buffer at 2× the threshold.

Reliability note: during the high-concurrency tuning runs the smolquery
server intermittently died with `SIGBUS / KERN_PROTECTION_FAILURE` on a
BEAM scheduler thread (fault address at a mapping's top edge — consistent
with a native stack overflow, likely in the DuckDB NIF). Nine crashes on
2026-08-10. Best reproducer: 64 VUs with a small flush threshold — 8 and
16 MiB killed the server 2-for-2 within minutes (smaller batches mean
proportionally more flush/NIF calls), while every ≥ 32 MiB run that day
survived, including the final crash-free 7-run baseline sweep. Crashed
runs were discarded and repeated. Tracked as a smolquery bug; the tuning
above assumes it gets fixed.

## Caveats

- k6 shares the machine with the server; its CPU is reported per run above.
- On a 429 the k6 script sleeps out the response's `retry-after` (capped at
  2 s) before retrying. The load-rig reference retried immediately, so its
  refused-heavy rows saw higher offered load than ours.
- Single 60 s run per configuration in the main table. Repeated runs during
  the tuning sweep put run-to-run variance at ±3–4%.
