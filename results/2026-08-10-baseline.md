# Baseline: smolquery vs ClickHouse ingest, 2026-08-10

First full harness run (`5a99fa6`). Closed-loop VU sweep, cold table each run,
identical 3,062-row × 62-column NDJSON body (~6.74 MiB). Per run: preflight,
20 s warm-up, 15 s pause, 60 s measured. Durability parity: smolquery fsyncs
before a 200; ClickHouse ran `fsync_after_insert = 1`,
`fsync_part_directory = 1`, `async_insert` off.

## Findings

**Drain rate decides the 32 VU collapse, not buffer size.** At 4/4 tuning,
~215 MiB in flight against `MAX_BUFFERED_BYTES=128 MiB` gave 78,586 rows/s behind
353,320 refusals (429 `buffer_full`). At 10/10 the same cap accepts everything
through 32 VUs and refuses 76 of ~9,600 at 64 VUs. A 256 MiB probe was worse.

**Low-VU rows are the ack-cadence floor, by design.** Below ~5 VUs no run reaches
the 48 MiB trigger, so each request waits out the 1,000 ms `FLUSH_INTERVAL_MS`:
p50 ~1.1 s at 2.9k–10.8k rows/s.

**smolquery leads ~5% at peak; ClickHouse wins below 64 VUs.** 480,569 against
457,472 at 64 VU, but ClickHouse leads at every level from 1 to 32 VU with much
better latency (13× at 1 VU, 24× at 4 VU). load-rig saw a 2.3× smolquery win
because ClickHouse-fsync runs 1.6–2.7× its reference numbers here, and because it
set a 32 VU smolquery peak against a ClickHouse arm measured only at 1 and 4 VUs.

**fsync costs ClickHouse only ~3% here** — 273,014 rows/s without it against
264,832 with it at 4 VU, where the reference paid 54% on CH 25.8 LTS
(359,141 → 165,814). The settings do apply, confirmed in `engine_full` and in
`system.events` (10 `FileSync` + 2 `DirectorySync` calls per insert, ~2.2 ms,
matching the p50 delta; 0 calls with `FSYNC=0`). A ~6.7 MiB insert builds a
*compact* part, so it syncs ~10 files, not 2 per column.

**Durability parity is real but weak on macOS.** Both arms use plain `fsync(2)`,
which on Darwin skips the drive write cache (`F_FULLFSYNC` does not). A 200 means
"past the page cache" on both arms, not "survives power loss".

## Tuning

### WRITE_POOL_SIZE / ENCODE_CONCURRENCY

From this sweep at 32 VU with the 256 MiB buffer. Stock smolquery defaults are
far lower: `write_pool_size: 1`, `encode_concurrency: 2`.

| pool/enc | rows/s | p50 ms | p99 ms |
|---|---|---|---|
| 4/4 | 306,287 | 302 | 567 |
| 6/6 | 336,106 | 270 | 593 |
| 8/8 | 352,524 / 376,385 (two runs) | 257 / 242 | 537 / 492 |
| 10/10 | 353,527 | 248 | 721 |
| 12/12 | 369,011 | 245 | 509 |
| 16/16 | 369,840 | 241 | 535 |

- **The knobs must move together.** 8/4 and 4/8 held throughput flat and produced
  429 storms: the narrower stage backs the buffer up.
- **The plateau starts at 8/8**, since variance is ±3–4% and 8/8 through 16/16
  sit inside that band. The baseline adopts 10/10, which equals
  `System.schedulers_online()` here, so it reads as "pool = enc = core count".
- **DuckDB threads are not the lever**: `WRITE_ENGINE_THREADS=2` (16 threads
  against 8) did 347,445, inside the noise. The ceiling is encode, buffer
  hand-off, flush cadence, or memory bandwidth.

### VU scaling and FLUSH_MAX_BYTES

Past 32 VUs, at the then-default 32 MiB flush, the closed loop was the limit:
383,597 / 394,353 / 414,700 / 419,237 rows/s at 32/48/64/96 VUs, then 382,362 at
128 as backpressure churn set in, with server CPU never above ~535% of 1000%.
**The best operating point is 64 VUs**, now in the sweep for both arms.

| flush size | rows/s | p50 ms |
|---|---|---|
| 8 / 16 MiB | server crashed | — |
| 32 MiB | 414,700 | 429 |
| 40 MiB | 459,845 | 373 |
| **48 MiB** | **491,098 / 510,924** (two runs) | 343 / 341 |
| 56 MiB | 497,993 | 334 |
| 64 MiB | 439,598 | 375 |

The baseline adopts 48 MiB. Against 32 MiB: +15% at 8 VU, −4–8% at 16–32 VU
(bigger batches fill slower at moderate load, near the variance band), +16% at
64 VU. 64 MiB probably crowds the 128 MiB buffer at twice the threshold.

### Reliability note

Nine crashes on 2026-08-10 during high-concurrency tuning: `SIGBUS /
KERN_PROTECTION_FAILURE` on a BEAM scheduler thread, fault address at a mapping
top edge — likely a native stack overflow in the DuckDB NIF. **Best reproducer:
64 VUs with a small flush threshold**, where 8 and 16 MiB killed the server
2-for-2 in minutes. Every run at ≥32 MiB survived, including the crash-free
7-run sweep. Crashed runs were discarded and repeated. Tracked as a smolquery
bug; this tuning assumes a fix.

## Caveats

- k6 shares the machine; its CPU is in the table above.
- On a 429 the script sleeps out `retry-after`, up to 2 s. load-rig retried at
  once, so its refused-heavy rows saw higher offered load.
- One 60 s run per configuration above; repeats put variance at ±3–4%.
